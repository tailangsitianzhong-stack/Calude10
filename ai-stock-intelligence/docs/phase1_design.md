## 0. 最初に確認すべき前提（設計を左右する事実）

| # | 前提 | 設計への影響 |
|---|---|---|
| 1 | **短期の株価の方向は、ほとんど予測できない**。単純なテクニカル・ルールの超過リターンは学習に使っていない期間で消え【第3段階】、有名なファクターも論文の発表後に38〜94%弱まった【第5段階】 | 予測AIは「当たる」ことを前提にしない。**比較の基準（ベースライン）モデル**を必ず置き、それを上回ったことが検証できたモデルだけを使う。上回らない間は、画面に「ベースラインと同等」と表示する |
| 2 | 企業の採点（投資魅力度）と、株価が上がる確率は別物 | 画面・データベース・APIで**別の概念として分離**する（指示書の要求どおり） |
| 3 | 実データの取得には、利用規約・商用条件を満たす**有料または登録制のAPI**が必要になる。無料で再配布可能な株価データはほとんどない | データ取得を「プロバイダー」として差し替え可能にする。**未接続のときは画面に明示し、架空の値は一切表示しない** |
| 4 | 日本で、報酬を得て個別銘柄の投資判断を助言する事業は、金融商品取引法の**投資助言・代理業の登録**が必要になりうる | 公開・商用化の前に専門家の確認を必須とする（15章）。画面の表現は「評価」「分析」にとどめ、「買い推奨」を使わない |
| 5 | この開発環境（クラウドのコンテナ）からは、一部のサイトが利用できない（Yahoo Financeは429、Stooqはボット確認、S&Pのサイトは403）。SEC EDGAR・FRED・French Data Libraryは利用できた | 開発中の動作確認は、利用できる公的データで行う。株価APIは、利用者のAPIキーで本番環境から接続する |

## 1. システムの範囲

**フェーズ7の完了時点で提供するもの**
- 日本株・米国株の分析（対象銘柄の範囲は、接続するデータAPIの契約範囲で決まる）

- リアルタイム（ティック）データ。初期版は**日次の終値ベース**（遅延データ）
- 日米以外の市場（設計上は拡張できるようにしておく）

```
       │ 書き込み                        │ 書き込み
┌──────┴───────── 取得ワーカー ─────┐  ┌──┴────────── 分析ワーカー ─────────┐
│ プロバイダー・アダプター            │  │ 品質検証 → 採点 → 予測 → 理論株価 │
│ (株価/財務/ニュース/経済/為替)      │  │ → 説明文（LLM）→ 結果の保存       │
│ 失敗しても他は止まらない（隔離）    │  │ 入力データの版とモデルの版を記録   │
└──────▲────────────────────────────┘  └────────────────────────────────┘
       │ 外部API（利用者のAPIキー。サーバー側の環境変数／秘密情報ストアで管理）
   株価API・財務API・EDINET・SEC EDGAR・FRED・ニュースAPI
```

**設計の原則**
1. **取得と分析を分離**：取得ワーカーが失敗しても、分析ワーカーとWeb画面は、最後に保存された正常なデータで動き続ける。古いデータには「古い」と表示する。
2. **API層は計算しない**：画面表示はデータベースの保存結果を返すだけにし、外部APIの障害が画面に波及しないようにする。
3. **すべての結果に「出所」を付ける**：どのデータ（取得日時・プロバイダー・データの基準日）と、どのモデル（版）から作ったかを、結果と一緒に保存する。
4. **予測は追記のみ**：一度保存した予測は、更新・削除できない（7章）。

| ファクター（検証用） | — | Kenneth French Data Library | 同左 | 学術用途の公開データ。商用での利用条件は要確認 |

**プロバイダー・アダプターの共通の約束**
```python
class PriceProvider(Protocol):
    name: str                      # 例 "jquants", "polygon"
    is_configured: bool            # APIキーが設定されているか
    def fetch_daily(self, security_id, start, end) -> list[DailyBar]: ...
    def status(self) -> ProviderStatus: ...   # 接続・最終成功時刻・遅延（分）・エラー

# 返すデータには必ず：取得日時、データの基準日時、遅延の有無と分数、プロバイダー名
```
- 同じ種類のデータに複数のプロバイダーを優先順位つきで設定できる（片方の障害時に切り替え）。
- **APIキーが未設定のプロバイダーは「未接続」**として扱い、その旨を画面に出す。代わりの架空データ（モック）を本番画面で使うことはしない。テスト用のモックは、テストコードの中だけに置き、画面には「テストデータ」と大きく表示する。

## 7. 予測の記録の改ざん防止

1. **データベースの制約**：`forecasts` テーブルには INSERT のみを許可し、UPDATE・DELETE をトリガーで拒否する。アプリのデータベース利用者には UPDATE・DELETE の権限を与えない。
2. **ハッシュ連鎖**：各予測の `record_hash = SHA-256(prev_hash + 予測の正規化した内容)`。1件でも書き換えると、それ以降のハッシュが一致しなくなる。検証ページで連鎖の整合性を常に確認・表示する。
3. **外部への日次の記録**：毎日の最後の `record_hash` を、外部（例：Gitリポジトリへのコミット、または公開されたログ）に記録し、データベースの管理者でも過去を書き換えられないようにする。
4. 結果（`forecast_outcomes`）は別テーブルに追記し、予測そのものは変えない。

## 8. AI採点システム（100点満点）

### 8.1 採点の原則
1. **業種テンプレート**：銘柄を次のテンプレートに分類し、テンプレートごとに小項目の指標と基準値を変える【第9段階：業種で評価方法が違う】。
   - 安定成熟型（生活必需品、公益、通信など）
   - 成長型（売上成長率が高く、利益が小さい・赤字の企業を含む）
   - 景気循環型（半導体メモリ、素材、海運、自動車など）
   - 金融型（銀行、保険、証券）
   - 判定は「業種コード＋過去の売上の変動の大きさ＋利益率の水準」で自動判定し、根拠を表示する。
2. **相対評価**：各指標は、同じテンプレート・同じ地域の銘柄の中での**パーセンタイル順位**と、その企業自身の過去5〜10年の推移の両方で採点する。成長企業と成熟企業を同じ基準で比べない。
3. **一時的な変動と構造的な変化の区別**：GAAP（会計上）の利益と、一時的項目を除いた利益の差、TTMと複数年平均の差を必ず計算し、差が大きい場合は「一時的要因あり」として信頼度を下げる【第2・7段階】。
4. **データ不足時は採点しない**：必要な指標の一定割合が欠けている小項目は「採点不能」とし、点数を推測で埋めない。総合点は、採点できた配点の合計で正規化して表示し、**カバー率**（採点できた配点÷100）を必ず併記する。**カバー率70%未満の銘柄は総合点を表示せず、ランキングから除外する**。
5. **古いデータの扱い**：財務データが最新の決算期から2期以上古い、株価が5営業日以上更新されていない場合は「古いデータ」として信頼度を下げ、一定以上古ければ採点不能にする。
6. **信頼度**：各項目に 高・中・低 を付ける。決まり方：データのカバー率、データの新しさ、一時的要因の有無、業種テンプレートの判定の確かさ、指標の過去の安定性。
7. **根拠の記録**：各小項目に「使った指標の値、比較対象（業種の中央値など）、点数の付け方」を保存し、画面に表示する。

### 8.2 項目と小項目（初期案。業種テンプレートで重みと指標を調整）

| 項目（配点） | 小項目（初期の配点） | 主な指標 | テンプレートによる違い |
|---|---|---|---|
| **成長性（20）** | 売上成長（6）、利益成長（6）、成長の質（4）、成長の持続性（4） | 売上・営業利益・EPSの3年CAGRと直近の伸び、オーガニック成長（開示がある場合）、成長率の変動の小ささ、受注・会社予想 | 景気循環型は「サイクルを通した成長」（5〜10年の平均）で評価。金融型は純営業収益とEPSの成長 |
| **財務健全性（15）** | 安全性（5）、利払い能力（4）、利益の質（4）、資金繰り（2） | 自己資本比率、ネット有利子負債/EBITDA、インタレストカバレッジ、FCF/純利益、アクルーアル、現金の残り期間（赤字企業） | 金融型は**CET1比率などの自己資本規制の比率、信用コスト**に置き換え（EBITDAは使わない） |
| **企業価値・割安度（15）** | 逆算した期待と実績・基準率の差（6）、理論株価との差（5）、相対マルチプル（4） | 逆DCFで必要な成長率と、過去の実績・基準率の比較【第7段階】、理論株価の範囲、業種内のPER・EV/EBITDA・PBRの順位 | 景気循環型は**正常化利益**と「好況の継続年数の逆算」【第9段階】。金融型は**ROTCEと株主資本コストによる正当化P/TBV** |
| **テクニカル分析（15）** | 中期トレンド（5）、モメンタム（12-1か月）（4）、ボラティリティ・下落の大きさ（3）、出来高・流動性（3） | 200日移動平均との位置、12か月（直近1か月を除く）の騰落率の順位、60日のボラ、最大ドローダウン、売買代金 | 全テンプレート共通。**ただし、指数のタイミングの単純ルールに超過リターンがなかったこと**【第3段階】を踏まえ、配点の妥当性はフェーズ6の検証で見直す |
| **競争優位性（10）** | 利益率の水準と安定（4）、ROICと資本コストの差の持続（4）、市場での地位（2） | 粗利率の5〜10年の変動、ROIC−WACCの持続年数、売上規模の業種内順位 | 金融型はROTCEの持続性と経費率 |
| **業界の将来性（10）** | 業界の成長（5）、業界の循環の位置（3）、構造的な逆風・追い風（2） | 業種全体の売上成長（データベース内の同業の集計）、在庫日数・受注などの循環指標 | 定性的な判断はLLMに作らせず、**集計できる数値だけ**で採点。数値がなければ採点不能 |
| **経済・市場環境（5）** | 金融政策・インフレ局面との相性（3）、為替の感応度（2） | 現在の局面（FF金利の変化、CPI）と、その業種の過去の局面別リターン【第4段階】、ドル円との相関 | 日本株は為替感応度の重みを上げる |
| **ニュース・材料（5）** | 直近の決算の内容（3）、重要な開示（2） | 会社予想の上方・下方修正、決算の前年比、重要な8-K・適時開示の有無 | ニュースの感情分析は検証されるまで配点に入れない（参考表示のみ） |
| **経営・事業戦略（5）** | 資本配分の実績（3）、株主還元の持続性（2） | 自社株買いの純減、減損の頻度（過去の買収の失敗）、配当性向（FCFベース）、希薄化 | 【第2段階：BodyArmor・Rockstarの減損】 |

### 8.3 小項目の点数の付け方（共通の方式）
- 各指標を同じテンプレート内のパーセンタイル（0〜100）に変換する。外れ値の影響を抑えるため、上下2.5%で打ち切る。
- 「低いほど良い」指標（負債比率など）は反転する。
- 小項目の点＝配点 × 指標のパーセンタイルの加重平均 ÷ 100。
- 例外のルール（ペナルティ）：債務超過、継続企業の前提の注記、監査意見の除外事項、上場廃止の基準への抵触などは、項目の点にかかわらず**警告**として表示する。

### 8.4 総合点の目安（指示書の区分）と表示
90〜100：非常に高い投資魅力度 / 80〜89：高い / 70〜79：比較的有望 / 60〜69：中立的 / 40〜59：慎重な判断が必要 / 0〜39：投資リスクが高い
- 総合点のすぐ横に「**この点数は投資魅力度の評価であり、株価が上がる確率ではありません**」と常に表示する。
- **フェーズ6で、点数と将来リターンの関係を検証**し、関係が見られない項目は配点を見直す（点数の高い銘柄群が実際に良い成績だったかを、点数の5分位ごとに確認する）。

## 9. 将来株価予測エンジン

### 9.1 予測の対象と定義
- 期間：1か月（21営業日）、3か月（63）、6か月（126）、12か月（252）。
- 予測するもの：その期間の**配当込みの対数リターンの分布**。
- 「横ばい」の定義：期間のリターンが ±k × σ_h（σ_h はその銘柄のその期間の予想ボラティリティ、初期値 k=0.25）の範囲。銘柄ごとに変動の大きさが違うため、固定の％にしない。定義は画面にも表示する。
- 出力：上昇・横ばい・下落の確率（合計100%）、期待リターン、株価レンジ（10%点・50%点・90%点）、要因、信頼度。

### 9.2 モデル（すべて、その時点で知り得たデータだけを使う）
| モデル | 内容 | 役割 |
|---|---|---|
| **M0 ベースライン** | 長期の市場平均のドリフト＋その銘柄のボラティリティ（EWMA・GARCH）で分布を作る。方向の情報は持たない | **比較の基準**。他のモデルはこれを上回らなければ使わない |
| M1 時系列 | ボラティリティ（GARCH）とリターン分布の裾（t分布・ブートストラップ）でレンジを推定 | 株価レンジの精度を上げる（裾の厚さ【第8段階】） |
| M2 モメンタム | 12-1か月の騰落率の順位、業種のモメンタム【第5段階】 | 方向の情報。日本ではモメンタムが弱かった【第5段階】ので、市場別に係数を推定 |
| M3 ファンダメンタルズ | バリュー、収益性（クオリティ）、低ボラティリティ、利益の修正 | 方向の情報（中長期） |
| M4 市場環境 | 金融政策・インフレ局面、イールドカーブ、信用スプレッド【第4段階】 | 市場全体のドリフトの調整 |
| M5 機械学習 | 上記の特徴量を使う勾配ブースティング（LightGBM）で、期間後のリターンの区分（上昇・横ばい・下落）を予測 | 非線形の関係。過剰適合しやすいので、検証を最も厳しくする |
| アンサンブル | 検証期間の成績（対数損失）で重みを決める重み付き平均。成績の悪いモデルの重みは0 | 最終の予測 |

### 9.3 確率の較正（キャリブレーション）
- ウォークフォワード検証の予測と実績から、確率の較正（等張回帰またはプラット法）を学習し、表示する確率を補正する。
- **「上昇確率70%」と予測した銘柄群が、実際に約70%上昇したか**を、確率帯ごとに検証ページで表示する（信頼区間つき）。
- 較正のサンプル数が少ない間は、確率を基準率（ベースライン）の方向に縮める。

### 9.4 予測の信頼度
「高・中・低」は、(1) そのモデル・期間・市場の過去の検証成績（ベースラインに対する改善の大きさと統計的な確かさ）、(2) 入力データの新しさとカバー率、(3) 予測分布の幅で決める。**ベースラインを有意に上回っていない間は、信頼度は常に「低」**とし、画面に「過去の検証では、方向の予測力はベースライン（市場平均）と同程度です」と表示する。

### 9.5 正直な表示のルール
- 精度が確認されていないモデルを「高精度」と表示しない。検証期間・件数・成績を必ず並べて表示する。
- 予測の期待リターンには、必ず株価レンジ（10〜90%点）と下落シナリオを並べる。

### 9.6 LLM（言語モデル）の役割
- 入力：保存済みの数値（採点の内訳・予測・理論株価・リスク）と、その根拠データのみ。
- 出力：初心者向けの説明文。**新しい数値を作らせない**。出力に含まれる数値は、入力に存在する数値と一致するかを機械的に照合し、一致しなければ破棄する。
- 説明文には「AIが生成した説明」と表示し、生成日時とモデル名を記録する。

## 10. 精度の検証（フェーズ6）

| 要求 | 実装方法 |
|---|---|
| 過去データによるバックテスト | 過去の各月末時点で、その時点のデータだけで採点・予測を再現し、結果を記録 |
| ウォークフォワード検証 | 学習期間を拡張しながら、直後の期間で検証（例：学習〜2015 → 2016を検証、学習〜2016 → 2017を検証…） |
| 学習データとテストデータの分離 | 期間で分割。最終テスト期間はモデル開発中に一度も見ない（保留） |
| データリーク防止 | 財務は**提出日（filed_at）以降**にだけ使う。株価は予測日の終値まで。期間が重なるサンプルの間に空白期間（エンバーゴ）を置く。特徴量の作成をテストで自動検査（未来の日付のデータが入っていないか） |
| 生存者バイアス対策 | 上場廃止銘柄を含むデータを使う（データAPIが提供する範囲で。提供しない場合は限界として表示）【第6段階】 |
| 予測確率の校正 | 9.3。確率帯ごとの的中率、ブライアスコア、対数損失、信頼性図 |
| モデル別の精度比較 | M0〜M5とアンサンブルを同じ期間・同じ銘柄で比較。差の有意性はブロック・ブートストラップで評価【第10段階：単純なt値は過大評価】 |
| 市場環境別の精度 | 上昇相場・下落相場、高インフレ・低インフレ、高ボラ・低ボラ別に集計 |
| 多重検定 | 試したモデル・設定の数を台帳に記録し、評価に反映する【第3・10段階】 |
| 取引コスト | 予測をランキングに使った場合の成績は、売買コスト込みで表示 |

**採用の基準**：新しいモデルは、保留期間でベースラインより対数損失が小さく、その差がブロック・ブートストラップで有意な場合だけ「active」にする。

## 12. セキュリティ

- APIキー・データベースのパスワード・LLMのキーは、サーバー側の環境変数（本番は秘密情報ストア）だけに置き、リポジトリ・ブラウザに出さない。`.env` は Git の管理対象外。
- ブラウザとは Next.js のサーバーを経由し、外部APIを直接呼ばない。
- 認証：セッションCookie（HttpOnly・Secure・SameSite=Lax）、CSRF対策、ログイン試行の回数制限。
- データベース：アプリ用の利用者は最小権限（予測テーブルは INSERT と SELECT のみ）。
- 入力の検証（検索文字列など）、SQLはパラメータ化。依存パッケージの脆弱性の定期チェック。
- 外部APIの呼び出しは、利用規約のレート制限を守る（待機・再試行・遮断）。

## 15. リスクと法的な注意（必ず確認が必要な事項）

1. **金融商品取引法**：不特定多数に個別銘柄の評価を提供すること自体は情報提供にとどまる場合もあるが、**報酬を得て投資判断の助言を行う場合は投資助言・代理業の登録が必要**になりうる。公開・有料化の前に弁護士等の専門家に確認する【要確認】。
2. **データの利用規約**：取引所の株価データ、ニュースの画面表示・再配布・保存には、提供会社との契約条件がある。個人利用の無料プランは、公開サービスでの表示を禁止していることが多い【要確認】。
3. **予測の限界**：本リポジトリの検証では、単純な予測ルールの多くは学習に使っていない期間で効果が消えた。予測の画面には常に検証成績を並べ、過大な期待を与えない。
4. **SEC EDGARの利用条件**：連絡先（メールアドレス等）を含むUser-Agentの送信と、毎秒10件までのアクセス制限を守る。
5. **LLMの費用**：銘柄数×更新頻度で費用が増える。説明文は変化があった銘柄だけ再生成する。
